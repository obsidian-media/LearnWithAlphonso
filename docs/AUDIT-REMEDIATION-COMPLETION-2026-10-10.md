## Transaction design and release handoff

The two new migrations are additive and must be deployed in filename order: `20261014100200_atomic_review_grade.sql`, then `20261014100300_atomic_lesson_completion.sql`. Both functions revoke public/anon/authenticated execution and grant only `service_role`. The web and Edge handlers authenticate and re-derive answer correctness before calling these RPCs; the client never receives the service key. Do **not** deploy the changed handlers before the corresponding migration. Because no remote migration was applied during this pass, the current worktree is a candidate, not a deployable proof of correctness.

F01's native queue sends its stable `queueIdentity` as `attemptId`, allowing the database to return the original grade result after a response is lost. The transaction locks the account and review row, checks the expected review timestamp/due date, atomically updates or retires the row, records a weakness-resolution event if applicable, and stores an attempt receipt. A repeated attempt cannot create a second event. Web grading uses the same atomic transition without a persisted queue identity. The local SQL tests cover success/replay, a deliberately failing event insert, and an attempt-identity collision. They do not cover real Supabase API authorization, network partitions, or a signed iOS queue drain.

F02's transaction locks the auth-user row to serialize completions across courses/devices and compares the caller's observed progress/completion/day versions before applying new values. A stale snapshot returns `conflict`, so neither caller claims success from a stale read. It writes six core tables in one database transaction. The web lesson UI no longer issues a separate `recordMisses` write before the completion. The local SQL tests prove an injected failure in the last feed-event insert rolls all earlier writes back. A lost response followed by a fresh completion can still re-enter post-commit achievement/AI-enrichment code; those effects need explicit idempotency/reconciliation design before F02 can be closed.

The first deployable candidate should: (1) run both migrations against a disposable full-schema Supabase database and confirm grants/RLS; (2) run web/Edge integration tests with simultaneous same-account requests, forced late-write failure and lost HTTP responses; (3) deploy migrations to the target environment before web/Edge code; (4) exercise the existing signed native client against both old and new endpoints; (5) pin web SHA, Edge SHA, database migration watermark and native build in one release manifest; (6) roll back callers first if needed, then remove additive functions only after no caller depends on them. No schema rollback is needed to keep old callers working.
